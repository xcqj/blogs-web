Loop Versioning：幂等发布与版本回写的设计取舍

博客的「发布」不是一个布尔翻转，而是一串必须原子的动作：内容落库、生成新版本、回写 current_version_id、同步标签关系。本文从 blog_article_version 的 append-only 约束出发，聊聊为什么值得单独维护一个「当前版本指针」。

版本表只允许 INSERT，禁止 UPDATE / DELETE —— 这是审计与回滚的地基，一旦破坏就再也补不回来。

为什么是 append-only

把每次「内容真正变化」的快照追加进版本表，好处是可追溯、可回滚、可 diff。代价是存储增长与「当前生效版本」需要显式指针。

  • 可追溯：任意历史版本可还原；
  • 可回滚：把指针指回旧版本即可，无需改历史；
  • 可 diff：相邻版本比对定位改动。

发布的事务边界

多表原子操作显式包在一个事务里，避免「版本写了但指针没回写」的中间态：

@Transactional(rollbackFor = Exception.class)
public void publish(Long articleId) {
    // 1. 内容变化比对 → 2. INSERT 新版本
    // 3. 回写 current_version_id → 4. 同步 tag 关系
}

内容变化才建版本

只有 title / summary / coverUrl / content 实际变化时才创建新版本，避免草稿反复保存制造无意义版本。

可见性三条件

公共可见必须同时满足三条件，任何公共查询都不得绕过：

字段取值含义
status1已发布
visibility0公开
del_flag0未删除

结论：版本指针 + 显式事务 是把「发布」这件小事做对的最低成本组合。
